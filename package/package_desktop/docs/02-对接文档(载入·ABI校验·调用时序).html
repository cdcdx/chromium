1. 产品定位 & 架构

定位："我们自己的 CefSharp"

桌面端定调（用户 2026-06-03 拍板）：类 CefSharp 的 .NET 内核封装库，像 CefSharp 一样易用，但叠加我们差异化的护城河能力。

维度方案原因
子进程模型CefSharp 式 subprocess 壳 exe（render.exe）
非 --single-process		dotnet.exe 不能当 chromium 子进程；保多进程崩溃隔离，符合反取证策略
跨端 UIAvalonia（非 WinForms/WPF only）拿到 Win/Mac/Linux 跨平台；OSR 帧 blit 到 Avalonia surface
差异化能力指纹反检测 + 代理（per-tab/transport）+ 插件系统CefSharp 没有，是护城河核心价值
交付形式arupa_kernel.dll + render.exe（第三方可直接引用）BrowserKernel 仓维护，类 CefSharp NuGet 包模式

进程模型

宿主进程（.NET / Avalonia）
  │  P/Invoke
  ▼
arupa_kernel.dll            ← C ABI 层（本文档接口）
  │  content API
  ▼
browser 主线程              ← RunContentProcess (std::thread) 内跑 UI loop
  │  IPC
  ├─ render.exe (renderer 子进程，--browser-subprocess-path)
  ├─ render.exe (gpu 子进程)
  └─ render.exe (utility 子进程)   ← --no-sandbox 模式（库式嵌入，LPAC 无效）

OSR 渲染模型

桌面无原生窗口。内核离屏合成（ArupaOffscreenWindowTreeHost + Aura），每帧通过 ArupaOsrSink.on_paint 回调 BGRA 像素，由宿主 .NET 层 blit 到 Avalonia Surface/WriteableBitmap。

3. DLL 加载 & ABI 校验

部署结构

应用目录/
├─ arupa_kernel.dll          ← 主内核 DLL（~130 MB）
├─ render.exe                ← 子进程壳（--browser-subprocess-path 指向它）
├─ arupa_kernel.pak          ← 资源 pak（或 content_shell.pak 临时替代）
├─ icudtl.dat                ← ICU 国际化数据
├─ snapshot_blob.bin         ← V8 快照（Windows x64）
└─ v8_context_snapshot.bin   ← V8 Context 快照

加载注意事项

  1. 使用 LoadLibraryEx(..., LOAD_WITH_ALTERED_SEARCH_PATH)，让 chromium 的 DLL 依赖在应用目录中解析（而非系统目录）。
  2. arupa_kernel_create 调用前必须完成 DLL 加载。
  3. ABI MAJOR 校验：从头文件取 ARUPA_KERNEL_ABI_MAJOR（当前 = 1），在 ArupaKernelConfig.abi_major 填入，内核会校验。
  4. pak_dir 须指向包含 arupa_kernel.pak（或 content_shell.pak）的目录，否则内核启动时 ResourceBundle 初始化崩溃。
// DLL 加载示例（ArupaKernelHost.cs 节选）
[DllImport("kernel32.dll", SetLastError = true, CharSet = CharSet.Unicode)]
static extern IntPtr LoadLibraryExW(string lpFileName, IntPtr hFile, uint dwFlags);

const uint LOAD_WITH_ALTERED_SEARCH_PATH = 0x00000008;

public static void LoadDll(string dllPath) {
    var handle = LoadLibraryExW(dllPath, IntPtr.Zero, LOAD_WITH_ALTERED_SEARCH_PATH);
    if (handle == IntPtr.Zero)
        throw new Exception($"LoadLibraryEx failed: {Marshal.GetLastWin32Error()}");
}

4. 调用时序

// 里程碑 A+B1 已验证的最小时序
宿主进程
  │
  ├─ LoadLibraryEx("arupa_kernel.dll", LOAD_WITH_ALTERED_SEARCH_PATH)
  │
  ├─ arupa_kernel_create(&cfg, &kernel)
  │     内部：裸 std::thread 跑 RunContentProcess(browser main loop)
  │           阻塞等 BrowserContext 发布（WaitableEvent）再返回
  │     返回 ARUPA_OK → content 真就绪
  │
  ├─ arupa_webview_create(kernel, &cfg, &cbs, &osr, &view)
  │     内部：PostTask 到 UI 线程同步建离屏 WebContents
  │           注册 WebContentsObserver（导航回调）
  │     返回 ARUPA_OK → WebView 就绪
  │
  ├─ arupa_webview_load_url(view, "https://example.com")
  │     内部：UI 线程导航
  │           ↳ 触发 on_page_started 回调
  │           ↳ render.exe 子进程 spawn（真渲染时）
  │           ↳ on_paint 回调出帧（✅ B2 runtime-verified）
  │           ↳ 触发 on_page_finished 回调
  │
  ├─ on_paint(pixels, width, height, dirty_x, dirty_y, dirty_w, dirty_h)
  │     ✅ B2 已验证：首帧 1280×800 BGRA；宿主将像素 blit 到 Avalonia WriteableBitmap
  │
  ├─ arupa_webview_destroy(view)
  └─ arupa_kernel_destroy(kernel)
⚠️ 线程规则：

should_intercept_request 回调在网络 IO 线程触发（同 AOSP），必须线程安全且快速返回。

其余导航/渲染回调在 UI 线程。.NET 侧对 UI 操作须通过 Dispatcher/InvokeAsync 封送。

ArupaWebViewCallbacks 在 arupa_webview_create 时传入，内核调用其中的函数指针通知宿主。

这份文档的「阶段」列是 2026-06 写的，之后再没跟过代码。 2026-08-31 逐条核过：标着「⏳ Phase2（未实现）」的 50 条里有 49 条其实早就实现了。

它的代价是实打实的（FB-P105）：对接侧读到 on_received_error 标着"未实现"， 以为内核没有导航失败回调，于是在每一次加载结束后往页面里 eval 一次 location.href 去反推——正常网页也照做。用户报「地址栏跳转特别慢」，把该功能关掉之后用户复测「不怎么慢了」。 ⇒ 一整条产品线（错误页）因为一句过期的文档而下线。

现在每种标记的证据强度（别读混）：

  • ✅ 已实现 —— 内核源码里有派发点（回调用这个口径）。
  • ✅ 已导出 —— 交付件 dll 的导出表里有这个符号。 ⚠ 这是必要不充分：空实现照样有符号。逐个的行为证据要看判据 （arupa_capi_*_test / arupa_navfail_test 那一批）。
  • ✅ runtime-verified —— 有判据真跑过。这一档最硬。
  • 🔴 声明了但从不派发 —— capi.h 里有声明，内核从来没调用过。 注册它不会报错，只是永远不触发。

⚠ 这一列现在由闸 C60 守着（build/roll/doc-impl-status-check.py）： 再标错会被当场拦下。但闸只判"有没有"，不判"好不好使" —— 后者是判据的事。

字段说明
on_paint(user, pixels, width, height, dirty_x, dirty_y, dirty_w, dirty_h)帧就绪回调。pixels = BGRA8888，行序 top-down，长度 = width*height*4。pixels 仅回调期间有效，必须同步拷走（不能持有指针异步使用）。dirty 区域为本帧实际更新的矩形（可直接 blit 脏区）。

宿主 blit 示例（Avalonia WriteableBitmap）

// C# P/Invoke on_paint 回调实现示例（Avalonia）
// ✅ B2 runtime-verified：on_paint 已真实触发（首帧 1280×800 BGRA，2026-06-04 smoke.exe 验证）
static void OnPaint(IntPtr user, IntPtr pixels, int w, int h,
                    int dx, int dy, int dw, int dh) {
    // 将 pixels 指针内容拷到托管 byte[]（必须同步）
    int byteLen = w * h * 4;
    var buffer = new byte[byteLen];
    Marshal.Copy(pixels, buffer, 0, byteLen);

    // 发到 UI 线程 blit
    Dispatcher.UIThread.Post(() => {
        using var wb = _bitmap.Lock();
        Marshal.Copy(buffer, 0, wb.Address, byteLen);
        _bitmap.Invalidate(new Rect(dx, dy, dw, dh));
    });
}

15 document-start 脚本注入（反指纹 + 模块命脉） PC 反指纹 + FingerprintInjector + ModuleScriptInjector 必须在页面脚本之前注入，在每帧 V8 context 创建时自动运行（类比 Chrome extension content_scripts@document_start）。on_page_started 时机太晚，且不能在回调内重入控制函数。
这是反指纹护城河 + 所有注入型模块的命脉，优先级最高。		 🔴🔴 是
16 nomad:// 自定义协议注册（整个 WebUI） WebUI home/settings/微应用/B 空间全走 nomad:// 自定义协议（standard + secure + fetch-enabled）。should_intercept_request 能替换响应但无法把 scheme 标为 standard/secure，影响 origin 计算与桥门控。没有它整个 WebUI 起不来。 🔴🔴 是
17 右键菜单 hit-test + 编辑命令 OSR 下无原生菜单。需：① 右键时回调 on_context_menu(link_url, image_url, selection_text, is_editable, media_type)；② 编辑命令 exec_command("copy"/"paste"/"cut"/"selectAll"/"undo"/"redo")。 🔴 是
18 整页截图 / CDP 通道（🟡 中等优先） on_paint 仅视口帧。建议：专用 capture_full_page(format, cb) 或 CDP 通道 send_devtools_command(method, params_json, cb)（更通用）。 🟡
19 web_prefs 键覆盖确认（🟡） set_web_prefs 支持键清单待补齐。至少需确认：dns_over_https.mode/templates、safebrowsing.enabled/enhanced、block_third_party_cookies、force_dark、load_images、javascript_enabled。 🟡 澄清
20 版本查询（🟢 低优） 需 arupa_kernel_version() → chromium 版本串 + 内核版本串。 🟢 低
21 IME 合成（🟢 低优，待澄清） send_key 是否覆盖输入法 composition（setComposition/commitText）？若否，需 send_ime_composition。 🟢 低，澄清
22 WebRTC IP 泄露策略（🟢 低优，待澄清） 内核反指纹 hook 是否已处理 force_webrtc_ip_handling_policy（代理场景防泄真 IP）？若否，需开关。 🟢 低，澄清
