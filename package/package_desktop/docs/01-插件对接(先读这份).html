Action 面的六个入口（2026-08-30 新加，FB-A060）

只有工具栏入口、没有独立主页的 MV3 扩展（截图 / 快速收藏 / 密码填充……）全靠这一组。 在这之前它们装得上、启得动、SW 显示"已注册"，而用户点不动 —— chrome.action.onClicked.addListener 挂得上，但没有任何东西会去触发它。

🔴 为什么点击派发必须内核做，你们模拟不了。 onClicked 的监听器活在扩展的 service worker 里。你们拿不到那个 JS 函数， 也不知道哪个监听器属于哪个权威扩展 id。按插件 id 写死业务逻辑的话，用户"看起来能用" 而插件代码一次都没跑 —— 那不是 MV3 Action 支持，是仿造。

⚠ 与安卓 ArupaPluginBridge 的同名方法逐条同源（内核那一层逐字节相同， 只差"宿主在哪一侧"）—— 同一个第三方插件装到两端，行为、错误码、"没人接"时的表现都必须一样。 两端分叉请立刻报回来。

四条纪律（每条都有它防的那个具体故障）

  1. userGesture 必须 true，缺省按拒处理。 内核不猜手势 —— 由你们如实断言。你们是可信嵌入方：手指点的、还是产品的 AI 点的， 都算你们的手势。插件侧没有任何入口能走到这条路 ⇒ AI 驱动不需要另一套授权模型。
  2. 🔴 navigationId 每次导航必须换新值。 它就是 activeTab 绑定的 document 维度。不换的话，旧授权会跟着用户 从新闻站走到网银站 —— 那正是 MV3 最小授权模型要防的。
  3. 🔴 撤销是你们的责任，内核不监听你们的标签页生命周期。 漏掉上面那三个 revoke 不会报错， 但插件会在它不该有权限的页面上继续有权限。
  4. popupPath 非 null ⇒ 你们去开 popup，内核不派发 onClicked（返回 1）。 MV3 里两者互斥，两样都做的话插件会以为被点了两次。
    ⚠ 这一支内核已经授了 activeTab —— popup 里的脚本同样要读当前页。

sequence 怎么用（有一处反直觉）

  • ✅ 同一个 extensionId 的两条快照：号大的是新的 ⇒ 只认号更大的那条， 迟到的旧事件就覆盖不了新状态。这是它唯一的用途。
  • ✅ 号全局唯一（一个进程一个计数器，不是每扩展一个）⇒ 不会撞号。
  • ❌ 别拿它跨扩展排先后：注册观察者那一刻的重放推的是各扩展各自的当前号 （历史值），顺序是内部 map 的 id 字典序 ⇒ 在全局看来是乱序的（实测拿到过 5,7,3）。 它们是"现状"不是"刚发生的变化"。按 extensionId 各存各的就无害。

activeTab 与 host_permissions 是两件事，别混

host_permissions（含 <all_urls>）＝清单里声明 → 装的时候用户同意一次 → 常驻；activeTab ＝一次真实手势 → 只对那个扩展 + 那一个 document 有效 → 导航/关闭/停用即失效。

⇒ activeTab 不是 host_permissions 的严格版，它是替代品。 插件想"一直有权限"，标准做法是声明 host_permissions， 不该由 activeTab 去补偿。 ⚠ 内核 HostPolicy 的默认档 2026-08-30 由 kStrict 改成 kConsent（产品拍板）——<all_urls> 现在保留， 不再被无声剥掉。改的理由：剥掉之后内容脚本没有可匹配的站点、且哪儿都不报错， 三方看到的是「装上了但什么都没发生」，那是最难查的形态，不是更安全的形态。

🔴 这一条必须跟着上面那句一起读，别读成「已经征得用户同意」： 内核侧 kConsent 与 kAllowAll 行为完全一样 （两档都原样保留 pattern，只是日志措辞不同），差别只在宿主要不要弹一次授权框—— 而宿主那个授权框还没做。⇒ 当下 kConsent 的实际效果等同 kAllowAll，用户此刻不会被问。选它是因为语义诚实、且给宿主留了接口， 不是因为已经有同意流程了。要改档位用 arupa_set_host_policy （0=STRICT / 1=CONSENT / 2=ALLOW_ALL）；读回当前档位用 arupa_get_host_policy。 ⚠ 这两个都是**配置**接口，可以在 arupa_kernel_create 之前调用 （2026-09-04 修好的 —— 此前按"先设档位、再建内核"这个最自然的顺序调用会崩）。

API 权限的档位 ApiPolicy（2026-09-04 新增）

上面那个开关管的是 host 权限（<all_urls>）。 本节这个管的是 API 权限（webRequest / cookies / management…）。两者此前待遇差很多：host 那条早就有三档， 而 API 那条一档都没有 —— 判 DENY 就无条件剥。

🔴 剥掉一个 API 权限的后果比剥 host 重得多：上游据 PermissionSet 生成绑定， 权限没了 ⇒ chrome.<ns> 整个对象不存在 ⇒ 扩展在 background 顶层就 TypeError ⇒ SW 注册失败 ⇒ 整个扩展起不来 （实测：真实商店网络加速类扩展在 background 顶层写 chrome.webRequest.onAuthRequired， 就是这样死的）。而在 Chrome 上，没有权限时对象照样存在，是调用才拒。

档位：arupa_set_api_policy / arupa_get_api_policy （0=STRICT / 1=CONSENT / 2=ALLOW_ALL， 默认 1 = CONSENT，产品 2026-09-04 拍板： 「chrome 既然允许开放我们也允许，只是指纹泄露之前必须是权限之类经过用户明确同意的」）。 越界值按最严处理并如实报，不许"看不懂就放行"。

🔴 三条边界，请连着上面一起读：

  • 「同意」这件事内核不强制 —— 与 HostPolicy 那段说的完全一样： kConsent 只是保留权限 + 在日志里说"宿主应当就此弹一次授权"， 内核既不弹也不记，宿主那个授权框还没做。 ⇒ 当下 kConsent 的实际效果等同 kAllowAll，用户此刻不会被问。 选它是因为语义诚实、且给宿主留了接口，不是因为已经有同意流程了。
  • 🔴 「面在」不等于「能用」 —— 保留权限之后 chrome.webRequest 对象会存在（顶层不再炸、SW 能注册），但调用拦不到任何东西： 判定仍然是 DENY_UNSUPPORTED(6) = 我们还没实现。 界面上必须把这两件事分开说，否则用户会以为"能用了"。
  • 特权逃逸类不受本开关影响 —— nativeMessaging（去起宿主机上的本地进程） 与 debugger（把 CDP 交给扩展）判 DENY_PRIVILEGED， 任何档位都照剥。产品那句话说的是指纹泄露面，而这两条是另一个风险类别 —— 不是用户点一下头就能抵消的。要开它们需要产品单独拍板。

🔴 隐私说明由内核给：arupa_mv3_perm_privacy_note（2026-09-08 新增，宿主必须显示）

传一个权限名（不是判定码 —— 与上下两条刚好相反，别传混），回一句 给普通用户看的中文：这条权限能读到你的什么。静态串，不用释放； 没有说明回 NULL。

由来：2026-09-08 产品拍板「说明隐私风险，而不是拒绝；涉及隐私问题都提示 用户，隐私当前泄露路径；优先保障功能可用」。此前 management / clipboardRead / system.* / <all_urls> 这 8 条一律阻装 —— 而实测两千多个真实商店扩展里有 678 个只被一条权限挡住，其余功能全好而用户一个都用不了。现在放行，而把风险说给用户。

🔴 宿主必须把这句话显示出来。不显示的话，我们就是把保护去掉了而什么都没换上 —— 那比原来那个一刀切拒更糟，因为用户连"这里有过一道门"都不知道。 ⚠ 而"宿主真的显示了"这一格内核验不了，要你那边的判据盯着。

⚠ 回 NULL = 这条权限没写隐私说明，不等于"它没有隐私风险"。 两者压成一个读数的话，宿主会把"我们还没写"显示成"这个插件很安全"。 ⇒ 缺说明不等于缺风险：拿不到时该显示一句通用提醒，而不是什么都不显示。

⚠ 只逐字匹配权限名：<all_urls> 取得到，而 https://*.example.com/* 这类 host pattern 一律回 NULL —— 逐站点的授权文案是站点权限那条路的事，内核这张表不做通配匹配 （做了就是第二处解析 host 模式的地方，而本仓已经因为"两处各认一套拼写"栽过一次）。

⚠ 它不改变"这条能力能不能用"：那 8 条在内核里一行实现都没有， arupa_mv3_perm_usable 仍回 0。产品那句「优先保障功能可用」指的是 别用拒绝去挡，不是"假装已经做了"。

判定码的名字由内核给：arupa_mv3_verdict_name（2026-09-04 新增）

传一个判定码，回它的名字（"ALLOW_MAPPED" / "DENY_UNSUPPORTED"…）。 静态串，不用释放。

存在的理由是别让每一端各抄一份码表。抄一份的代价已经收过两次利息： 内核自己的判据抄漏过两次（加码 5、加码 6），两次都是"判据全绿而证据印成 ?"； 对接端 2026-09-04 也报他们那份只声明了 0/1/5，于是内核在 ALLOW 一族加码的那一刻， 他们会静默判成"被拒"（方向安全，但不可观测）。

🔴 越界/认不出的码回 NULL，不回任何字符串 —— 因为 4 本身就叫 DENY_UNKNOWN，回它就分不出"码是 4"和 "这个码我不认识"。回 NULL 才分得开，而且不可能被静默当成一个判定名 印到界面上。

⚠ 它不解决"客户端比内核旧"：旧客户端拿到一个新码仍然不认识。那一半要靠你自己的 "未知码"分支 —— 正确处理是按拒 + 明说"本版本不认识这个码"， 不许猜成放行（deny-by-default 的同一条）。

⚠ 采用这个导出的条件是生产基线含它，不是"我这台机器上的 current 有了" —— 在含它的那一版成为生产基线之前，直接 P/Invoke 会 EntryPointNotFound。

还没做 / 刻意不收的

按标签页的 Action 状态没做。MV3 允许 setBadgeText({text, tabId}) 只改一个标签页，而内核现在只有"每扩展一份"。⇒ 带 tabId 的调用内核 如实报错，不静默当成全局设 —— 静默的话插件以为只改了一个标签页，其实改了全部。

划给你们的那几个内核刻意不收：setIcon / badge 颜色 / openPopup / getUserSettings —— 纯渲染或纯 UI 动作， 内核既答不出也不该记。

三、从零走一遍

① 初始化时设扩展根，并当场回显确认 
var kernel = new ArupaKernel(new ArupaKernelOptions { /* … */ });

string extDir = Path.Combine(appDataDir, "extensions");
Directory.CreateDirectory(extDir);
kernel.SetExtensionRoot(extDir);

// 🔴 这一行别省 —— 它是这条线上唯一能当场发现"没生效"的地方
if (!string.Equals(kernel.GetExtensionRoot(), extDir, StringComparison.OrdinalIgnoreCase))
    Log.Warn($"扩展根没设进去: 期望 {extDir}, 内核回显 {kernel.GetExtensionRoot()}");

⚠ 别和 SetPluginRoot 传同一个目录（坑 1）。 ⚠ 回显为空串有两种可能：真没设进去，或者 dll 太旧没有这个导出（坑 5）。

② 写一个最小扩展（先用它验通路，别一上来就上真插件） 
extensions/hello/manifest.json
{
  "manifest_version": 3,
  "name": "hello",
  "version": "1.0",
  "content_scripts": [{
    "matches": ["https://*/*"],
    "js": ["cs.js"],
    "run_at": "document_end"
  }]
}

extensions/hello/cs.js
document.title = "EXT_RAN";

把 document.title 当哨兵是有意的：内容脚本跑在隔离世界， 但 DOM 是共享的 ⇒ 你在主世界（或 devtools）读 title 就能判断它跑没跑。 读某个隔离世界里的变量反而验不了。
⚠ MV3 的 content_scripts 只匹配 http/https， 拿 data: 页去验会得到一个永远不注入的假红 —— 内核自己那份 runtime 判据 就是为此在进程内起了一个本机 HTTP 服务。

③ 开一个页面，看哨兵在不在

就这样，不需要调任何"装载"。内核在 renderer 进程 ready 时扫扩展根，逐个下发。

var view = kernel.CreateWebView();
view.LoadUrl("https://example.com/");

// 页面加载完之后, 从**主世界**读回 title
string r = await view.SendCdpAsync(
    "Runtime.evaluate",
    "{\"expression\":\"document.title\",\"returnByValue\":true}");
// 期望 r 里的 value == "EXT_RAN"
⚠ 为什么这里绕了 CDP：主世界 eval 在 .NET 门面里没有公共包装（2026-08-26 现读）。 C ABI arupa_webview_eval_js 是有的（在交付件的导出表里）， Interop.cs 里也声明了 —— 但 ArupaBrowser.cs 没往外给一个 EvalJsAsync 之类的方法。门面里有的是 InjectIsolatedJsAsync（隔离世界），那个读不回主世界的 document.title。
⇒ 两条路都行：走 CDP Runtime.evaluate（上面这样，门面现成）， 或自己 P/Invoke arupa_webview_eval_js（签名在 capi.h）。
⚠ 这条缺口已记进内核侧待办，别读成"内核没这个能力" —— 缺的只是托管侧那一层包装。
⚠ 别只看日志里那句「N 成功 / 0 失败」。 它只证明发过去了，不证明跑起来了。本仓栽过：日志报 N 成功而页面里一个都没生效。 判据要落在页面内容上（就是上面那个哨兵）—— 2026-08-25 PC 侧那次 5/5 的回执正是这么做的，做法是对的。
④ 要做启停？先拿 id 
var exts = kernel.ListExtensions();          // List<(string Id, string Dir)>
foreach (var (id, dir) in exts)
    Log.Info($"扩展 {id} ← {dir}");

kernel.SetExtensionEnabled(exts[0].Id, false);   // 立刻失效
kernel.SetExtensionEnabled(exts[0].Id, true);    // 装回来
⑤ 装了带 background 的扩展？问一句它到底起没起 
var st = kernel.ExtensionServiceWorkerState(id);
switch (st)
{
    case ArupaKernel.ExtensionSwState.Registered:      /* 正常 */              break;
    case ArupaKernel.ExtensionSwState.NoServiceWorker: /* 内容脚本型, 正常 */   break;
    case ArupaKernel.ExtensionSwState.NotRegistered:   /* 有 SW 但没起来 */     break;
    case ArupaKernel.ExtensionSwState.Unknown:         /* 内核不认识这个 id */   break;
}

四、五个坑

坑 1（两个根别混）在第一节。下面是另外四个。

🔴 坑 2：扩展 id 不是目录名。 MV3 的 id 有两种来源 —— manifest 里有 key 时从 key 派生， 否则才从路径派生。本仓实测过 TunnelBear 的 id （omdakjcmkglenbhjadbccaookpfjihpa）就来自 key。

所以：按你自己起的目录名去调 SetExtensionEnabled，会静默不生效 —— 不报错，用户点了"禁用"而扩展照样在跑。 ⇒ 一律先 ListExtensions() 拿权威 id。
🔴 坑 3：内核不是文件系统监听。 自动下发发生在新 renderer 进程 ready 的那一刻 —— 它扫一次盘，就这一次。

两个直接后果：
  • 同一个页面里刷新不会重扫。刚装完的扩展，用户在当前标签页按刷新 —— 不生效。 要立刻生效就调 RescanExtensions()。
  • 设根晚了不要紧。你在页面已经开着之后才调 SetExtensionRoot， 内核会回头补发给那些已经 ready 的进程。 这条 2026-08-25 才真正接上 —— 在那之前 "先起页面、后设根"的进程永远拿不到扩展，且零日志。
⚠ 桌面这边还有一条安卓没有的：换 partition 会开新 renderer ⇒ 那条路走的是"扫盘" 而不是"补发"。写判据时这两条路要分开验，否则你以为在验补发、实际验的是扫盘 （内核自己那份 runtime 判据的第一版正是这么错的，摘掉补发它照样绿）。
🔴 坑 4：ListExtensions() 回答的是"内核已经认识哪些"，不是"当前根下有哪些"。

两条都别当判据用错：
  • "已登记" ≠ "当前启用" —— 被 SetExtensionEnabled(id,false) 禁用的仍在表里。
  • "已登记" ≠ "在当前扩展根下" —— 换了根之后，旧根那些扩展仍在表里。 登记发生在"解析成功并下发过至少一次"那一刻，而这张表只增不减。
🔴 第二条是 2026-08-25 你们实撞的：反测拿"换成空根之后列表应该变空"当判据，当场红 —— 判据本身错了，不是内核错了。内核此前只写了「已登记 ≠ 当前启用」，少的正是这条， 所以这不是你们的问题，是文档缺口，已补进 capi.h 与门面注释。
⇒ 要判"当前根下有什么"，请自己扫目录；ListExtensions() 只用来拿权威 id。
🔴 坑 5（PC 独有）：旧 dll 上，门面是静默失败的。

这几个方法在 .NET 门面里都 catch (EntryPointNotFoundException) 后不抛 —— 因为宿主对内核版本无能为力，抛了只会让整个初始化失败。但这意味着：
dll 版本不够时你看到的实际后果
SetExtensionRoot（< MINOR 11）什么都没有 扩展一个都装不上（内核日志里有一条 "扩展根未设置" 的 WARNING 兜底）
SetExtensionEnabled（< MINOR 12）什么都没有 禁用不生效 —— 该按内核版本把 UI 上的开关置灰，而不是假装它成功了
ListExtensions（< MINOR 12）空列表 与"没有扩展"同形，分不开
GetExtensionRoot（< MINOR 11）空串 与"没设"同形，分不开
ExtensionServiceWorkerState（< MINOR 13）Unknown(-1) 与"内核不认识这个 id"同形。不是"没有 SW"，也不是"起来了"
⇒ 拿这几个方法写判据之前，先确认手上 dll 的 ABI MINOR。 最省事的做法是启动时读一次导出表或调一次 GetExtensionRoot 探测。
⚠ 还有一条不是坑、是版本线：带 background.service_worker 的清单， 在 152.0.7977.42+11 之前整个装不上（FB-P090）。 两层根因都在内核侧、都已修：① chrome-extension 没注册成 scheme ⇒ Extension::Create 整个失败；② SW 注册报 kErrorNetwork(10) —— 扩展 URL loader 工厂写了但零注册点。
⇒ 拿更早的件试会得到"扫不到"，那不是三方写错了清单。

五、内核提供了什么（以及没提供什么）

内核抽了 chromium 自己的 extensions 层，所以不是我们另写了一套近似实现：

能力由谁执行
内容脚本（matches / run_at / css / all_frames） 上游 ContentScriptsInfo → UserScript → UserScriptSet::UpdateUserScripts ⇒ 官方语义
manifest 解析、权限模型、扩展 id 派生上游 extensions/common
background service worker 内核起（chrome-extension:// 资源 loader 已接， 152.0.7977.42+11 起）
chrome.storage内核 per-plugin 隔离存储（ArupaPluginStorage）
chrome.* bindings / 消息通道内核（renderer 侧 Dispatcher 已装配）
✅ 一句话：标准 MV3 扩展的内容脚本这条路，你不用自己再注入一遍。 如果宿主里还留着"页面加载完自己 InjectIsolatedJsAsync 注内容脚本"那半， 可以让内核官方路径独占 —— 它更完整（带 SW / chrome.* / 消息通道）。
⚠ 但内置插件（不在扩展根之下、内核扫不到的那些）仍走你自己的注入，这个分工是对的。

没提供的 / 要你自己接的：

  • 启停状态不落盘。内核不替你记住用户的选择 —— 那是你的插件管理页该持久化的。 宿主每次起来后按自己的记录重设一遍。
  • 权限判定内核只给结论，不弹 UI。见下节。
  • DNR 规则引擎本体是你的，内核只给逐条护栏（CheckDeclarativeRule）。

nomad.* 那组产品扩展指令 —— 目标形态，端上尚未切换

⚠ 这一小节写的是 (甲) 方案落地之后的形态，不是今天桌面跑的形态。 产品 2026-08-25 拍板：桌面改用内核交付件里那份 plugin-runtime/nomad-plugin-runtime.js（FB-P082 甲）。 但 PC 侧还没切 —— 今天跑的仍是自有等价实现（NomadWebUI 里那约 2,100 行 清单解析 / 装载 / 登记）。照下面写完发现端上不是这样，是因为还没切，不是文档错。

nomad.* 这个 JS 命名空间只有那一份实现；内核 C++ 提供的是执行面， 不提供 nomad.* 本身。四条对接要点（都现读自源码）：

①加载入口交付件里那份就是，不用另找： dist/win/current/plugin-runtime/nomad-plugin-runtime.js（随每次交付更新）。 两种拿法都行 —— ESM import { NomadPluginRuntime } from './nomad-plugin-runtime.js'， 或页面里用它自己挂的 window.NomadPluginRuntime + window.__nomadPluginRuntimeVersion。
②宿主要实现 host.* 这是四端唯一不同的那一块，由各端宿主注入。运行时现采 22 个方法名。 桌面已有的等价物（权限判定 / 存储 / 出口路由 / 位置查询）接过去即可，主要是改名与签名。
⚠ 宿主可以少实现 —— 运行时对缺失有四档处理 （notSupported / 返回 null / 抛错 / 按拒），但不能改运行时怎么调它。
③自己扩展指令 走 registerNomadCommand(name, impl, meta)（页面里拿不到 ESM import 时用 window.registerNomadCommand）。
⚠ 只给宿主 —— 插件跑在自己的上下文里，看到的是 nomad.*，摸不到这个 window。
④三个名字永远注册不上 route / transport / identity（特权轨）。 这不是风格约束是安全边界，见 docs/spec/kernel-plugin-security-model.md。

六、权限判定（内核给结论，UI 归你）

ArupaMv3.MapPermission(perm) 逐条判清单里的权限。 🔴 判定在内核（三端同一份），宿主不重写 —— 各端各写一份必漂。

返回含义你该做什么
0 AllowMapped映射到某个受控 cap.* （用 PermissionCapability 拿名字）按那个 cap 授权
1 AllowLowRisk低风险，直接给放行
2 DenyPrivileged特权（debugger / nativeMessaging / 阻塞式 webRequest / proxy…） 拒装或剥权 + 审计
3 DenyFingerprintRisk指纹风险（management / cookies / history / <all_urls>）同上。
🔴 management 例外（2026-09-19 起, ABI MINOR 22）：不拒，允许启用并弹授权框； 用户选完调 SetExtensionPermissionConsent(id, "management", 同意?)。 同意 ⇒ management.getAll 转你们的扩展 API 处理器答真实名单；不同意 ⇒ 内核替代应答 []。 授权记录由你们持久化，每次起内核后重新告诉一遍。见 FB-P181。
4 DenyUnknown内核不认识 ⇒ 保守拒拒
5 VendorNamespacenomad.*：认识，但不该由它答 去问对应那套判定（nomad.route → ArupaRoute.Check）
🔴 5 不是放行。拿到它就当放行，等于凭一个名字前缀发能力。 也别把它当 4（保守拒）处理 —— 桌面 2026-08-19 实跑撞过： 那样做会让加速类插件在装的那一刻就被摘掉权限。 ⚠ 也别自己写前缀判断：边界由内核给。

ArupaInject.Check(...) 判每次注入。 判定顺序是先红线、再声明、后授权，顺序不能反 —— 没声明的域名连问用户的资格都没有，否则插件可以靠"运行时请求任意域名"绕开清单审核。

0Allow放行
1DenyNotDeclared清单没声明 —— 不该弹授权，直接拒
2DenyNotGranted声明了没授权 —— 这个才该弹授权
3DenyProtectedScheme非 http(s)：内核页 / devtools / file / about
4DenyProxiedHost被代理接管的域名（与 DNR 护栏同一条红线）
5DenyBroadNotGranted声明含 <all_urls> 但未给全站授权 —— 单列一类，好让 UI 把"要读你所有网页"讲清楚

还有 NeedsReconsent(old, new, granted)：插件更新后声明范围扩大了要重新征求同意。 防的是一条真实可走的路 —— 装时只声明一个站、用户点了同意，更新后清单悄悄加 <all_urls>，于是它能读全网，而用户什么都没再点过。

出口路由的档位（ArupaRoute.Check）

0Allow放行
1AllowNeedsConsent未签名 + global：先要用户点头一次
2DenyScopeNeedsSign未签名 + 更细作用域：拒
3DenyNotDeclared清单没声明 nomad.route / proxy
4DenyUnknown认不出的作用域 / 参数不全 / 兜底
🔴 拿到 2（DenyScopeNeedsSign）时必须报错，不许静默降级成 global。 那会让插件以为分流生效了，而实际全局出口都变了。
⚠ is_signed 不是入参 —— 内核自己查 active 签名包。 做成入参等于把信任交给调用方，那就没有门控了。

六点五、我的插件装不装得上 —— 一条命令自己验

交付件里带了这个工具：arupa_plugintest.exe， 与内核同目录（解开的交付包里是 kernel/）。 ⚠ 2026-09-18 起交付包分两份：它只在测试包 arupa-win-<交付id>-test.zip 里， 生产包 arupa-win-<交付id>.zip（集成进发给用户的 App 用的那份）不带它。 2026-08-28（交付 id +17）起才有 —— 在那之前它只编进内核仓的开发目录、 从没随件发出来，所以「没有内核就没法测插件」这句话在字面上是成立的。现在不成立了。

cd <解开的交付包>\kernel     ← 必须在这个目录里跑（它要找同目录的 pak / render.exe）
arupa_plugintest.exe <放插件的目录> <插件 id>

例:  arupa_plugintest.exe D:\my-plugins my-accel
     ⇒ 找 D:\my-plugins\my-accel.arupa-plugin\
退出码屏幕上意思下一步
0核心(加载器) PASS ✅ 验签过了 · 引擎在独立沙箱进程里起来了 · SOCKS 端口在 listen 装得上，往下做功能
2BLOCKED: 前置资产不在 目录/包不在，或包里少 manifest.json 不是内核问题：包没放对，或没签
3核心(加载器) FAIL 走进加载链之后失败了 把整段输出发内核会话，那是内核该看的

⚠ 它验的是装载链（验签 → 起沙箱子进程 → 端口 listen）， 不验引擎转发得对不对 —— 那是插件方自己的功能测试。 过了只说明「这个包在这个内核上装得上」。

🟢 通过时输出里会有一个 engine_pid=… —— 那是另一个进程： 引擎跑在低完整性令牌的子进程里（交付 id +15 起），不在内核进程内。 ⇒ 沙箱与「引擎自己起本地 SOCKS」是同时成立的， 你们和插件方都不用为沙箱改任何东西。

⚠ 这一节讲的是传输类插件（.arupa-plugin 包，带 native 引擎）。 MV3 扩展那条线不走这个工具 —— 两条线的区别见本文第一节。

七、出问题时看什么

现象先做这一步多半是
一个扩展都没生效调 GetExtensionRoot() 看回显 空串 ⇒ 根没设进去（坑 1），或 dll 太旧（坑 5）
回显对，但页面里没反应看内核日志里内容脚本待发那条的 匹配模式=[…] matches 没匹配上当前 URL（尤其：拿非 http(s) 页面验）
装完新扩展刷新没用调 RescanExtensions()坑 3 —— 内核不是文件系统监听
点了禁用还在跑把传进去的 id 与 ListExtensions() 的对一下 传的是目录名（坑 2）
带 background 的扩展"扫不到"调 ExtensionServiceWorkerState(id) 拿到 -1 且 id 确实对 ⇒ 清单在解析层就没过；件早于 +11 的话就是 FB-P090
SW 装上了但 background 没跑拿到 0，去看 [arupa][sw] 注册失败 … status=SW 注册本身失败，把 status 报回内核会话
某个方法"不存在"对一下 dll 导出表与 capi.h wrapper 快照旧了（第二节那条红框），或 dll 版本不够

⚠ 另外：ArupaKernel.LastErrorJson() 是 thread_local 的 —— 谁调的谁读，且只在紧接着的失败之后读才有意义。 null 不等于"上一次成功了"，只是本线程没记录过失败。 对 async 宿主尤其要小心：await 之后的续体常常已经换线程了。

八、内核侧验到哪一步（别读成"都验过了"）

桌面这一端有 runtime 判据（arupa_extdispatch_test）：起真内核 + 真 renderer + 进程内一个本机 HTTP 页，装一个改 document.title 的探针扩展，从主世界读回 title。 在 152.0.7977.42+11 的交付集上 12 PASS / 0 FAIL。覆盖：
  • 观测本身有效（页面真加载出来了）+ 没设根时的对照组
  • 设扩展根 ⇒ 内容脚本真跑了
  • 先起页面、后设根 ⇒ 补发生效
  • 内核交得出权威 id
  • 禁用之后内容脚本不再跑；重新启用又跑起来
  • 带 background.service_worker 的清单装得上、SW 注册得上（T5a–T5e，FB-P090）
反测实做过：同一个 test exe 配交付原件那份 dll ⇒ T5b/T5c 当场红、其余 8 条全绿。 摘掉补发 ⇒ 补发那条 FAIL；让禁用不记进禁用集合 ⇒ 禁用那条 FAIL。
⚠ 它不验这些，别读成验过了：
  • "禁 A 不影响 B" —— 只有一个探针扩展，装两个只禁一个这件事没覆盖
  • SW 里的 chrome.* 到底能用到什么程度 —— 验到"SW 注册得上"为止。 chrome.proxy 真去换出口没验（那要权限映射 + 出口路由两条线）
    🔴 这一格 2026-08-26 当天就被撞上了（FB-P091）：SW 已经 Registered，而 content script 的 chrome.runtime.sendMessage 拿不到任何回应 —— 读回是 null 而不是 no-response， 说明回调压根没触发、连 lastError 都没走到。
    ⇒ 消息通道这一层现在是不通的，别按"SW 起来了就等于 chrome.* 能用"来设计。 它挡着 chrome.proxy 那条线 （background 与外界唯一通路就是消息），但不必然挡死 —— 若 SW 能在启动时自己调 chrome.proxy，那条仍可单独验。
  • css 注入 / 权限映射在真扩展上的表现 —— 权限映射有独立的单元判据， 但没有"真扩展装上去按这个结论走"的端到端
  • 你们那一层 —— 自己的安装流程、partition 策略、真实扩展而非探针

所以下面这几条只有你们验得了，也正是最该验的：

  1. 一个真实扩展（有 SW、有 chrome.*、有 css）装上去，页面里真的跑起来
  2. 装两个扩展只禁一个 ⇒ 被禁的停、另一个照常
  3. 装完新扩展 → RescanExtensions() → 已开着的页面里生效
  4. 宿主重启后按自己的记录重设一遍启停状态（内核不落盘）
