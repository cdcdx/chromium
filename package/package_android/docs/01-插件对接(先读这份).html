Arupa 内核 Android · MV3 插件对接文档

内核 152.0.7977.42+6 · 2026-08-25 · 本页讲 怎么用这个内核装载并管理 MV3 扩展。 工程侧怎么摆（AAR 怎么引、初始化序列、打包）看 对接文档； 与 AOSP WebView 的差异看接入清单；逐个方法查 API 参考。

📍 这份文档的 API 表不是手写的。 下面每个方法都是从交付件本身读出来的 （dist/android/current/<abi>/arupa-kernel.aar 里的 classes.jar 方法表）。 如果你手上的 AAR 里没有某个方法，那就是版本不够，不是文档写错—— 本页对应的是 152.0.7977.42+6 及以后。

一、先分清两条插件线（混了必踩）

内核里有两条互不相干的"插件"通路，名字像但完全不是一回事。 这是本仓出过两次事故的地方（FB-A050），所以放在最前面。

MV3 扩展线（本文讲这条）传输插件线
装什么标准 Chrome MV3 扩展（解包后的目录，含 manifest.json） 我们自己签名的 .arupa-plugin 包（native 引擎）
设根ArupaPluginBridge.setExtensionRoot(dir) ArupaPluginBridge.setPluginRoot(dir)
怎么装不用调装载——把目录放进扩展根，内核自动下发 load(pluginId) 验签 + 起引擎
做什么用内容脚本、chrome.*、侧栏、右键菜单…… 网络出口（三方加速客户端）
要签名吗不要要（Ed25519）
🔴 坑 1：两个根别传同一个目录。 FB-A050 就是这么出事的——宿主 initialize 时先设了扩展根， 之后又把传输根设成 files/transport-plugins， 而当时两者共用一个字段 ⇒ 后写覆盖先写 ⇒ 放在 files/plugins 的扩展一个都没下发，而且不报错。

现在两者已彻底分开，且内核不会在没设扩展根时拿传输根顶替—— 它宁可一个都不发，并在日志里说清楚。看到这条就是没设： 
[arupa] 扩展根未设置(没调 ArupaPluginBridge.setExtensionRoot), 跳过扩展下发。

二、你要用的 API（co.arupa.plugin.ArupaPluginBridge，全 static）

方法做什么什么时候调
setExtensionRoot(String dir) 告诉内核去哪找 MV3 扩展。该目录下每个带 manifest.json 的子目录算一个扩展。 任何时候都行——见下面"坑 3"。
listExtensions() → JSON 列出内核已经认识的扩展：[{"id":"…","dir":"…"}]
⚠ 是"已经认识哪些"， 不是"当前根下有哪些" —— 见坑 4		 要对某个扩展做启停之前，先用它拿 id。
setExtensionEnabled(String id, boolean on) 单个扩展的启停。关掉 = 之后的扫描跳过它 + 对已经开着的页面发卸载（立刻失效）。 用户在你的插件管理页点开关时。
setExtensionApiHandlerCtx(ExtensionApiHandlerCtx cb) 收扩展调用时额外给一份内核组装的可信上下文：profileId · extensionId · installGeneration · contextType(page / serviceWorker) · frameToken 与 frameTreeNodeId(或 workerVersion) · incognito · userActivation · permissionSnapshot。
🔴 身份由通道绑定决定，渲染进程自报的不作数 —— 插件在 payload 里塞同名字段不会被采信。
⚠ 原来的 setExtensionApiHandler 行为不变，不接这个也照样跑。
⚠ 我方没有 per-document 标识 ⇒ 给的是帧令牌 + 帧树节点号，没有拿它冒充 documentId。		 宿主要按"谁在调"做鉴权、配额或审计时。
setExtensionApiCancelListener(ExtensionApiCancelListener l) 页面关了 / Service Worker 停了 / 扩展被停用 / 安装代次变了 ⇒ 内核先通知你，再作废在途请求，插件那头拿到明确错误（不再永远 pending）。 宿主接到调用后会起异步任务时——不接的话你会为一个没人再要的结果继续干活。
setExtensionInstallGeneration(String id, long gen) 把这个扩展的安装代次告诉内核。内核只做单调校验（回退的代次拒收）； 代次一变，旧代次的在途请求一律作废。 装 / 升级 / 重装某个扩展之后。
setApiTimeoutOverride(String prefix, int seconds) 按方法名前缀放宽应答时限（默认 10 秒）。 有需要用户交互的调用时（选文件、授权确认这类，默认 10 秒必超时）。
setTabIdForWebContents(WebContents wc, int tabId) 把这个标签页的编号告诉内核。 chrome.tabs.sendMessage(tabId, …) 与 sender.tab.id 都靠它——那个整数是宿主的命名空间（tabs.query 答出去的就是它）， 而内核认识的只有 WebContents。
⚠ 一般不用直接调它： ChromiumWebView.setTabId(int) 是同一件事的实例版， 而且带 pending 存根（WebContents 还没建也能调）。
⚠ 传负数 = 解绑。内核不猜：没声明过的号一律投递失败并留一行日志， 不会退化成"只有一个标签页那就是它"。		 建标签页时一次；每次导航后重复调也安全（登记幂等， 而 WebContents 可能因渲染进程崩溃被重建）。
setExtensionUserLoaded(String id, boolean userLoaded) 断言"这个扩展是用户自己加载的开发包"。
🔴 只影响 nativeMessaging 那一档判定：一个包要拿到它，要么有我们的签名，要么宿主为它背书； 两样都没有 ⇒ 拒（NM_NEEDS_SIGNATURE_OR_USER_LOAD）。
⚠ 这不是"用户点一下同意"那种授权——拉起本地进程的后果用户看不见也管不了， 一个确认框描述不了它。
⚠ 内核不猜：没调过 ⇒ 按"不是用户加载的"算；传 false 是撤销。		 用户从本地目录装了一个开发包时。
rescanExtensions() 重扫扩展根，把新发现的扩展补发给已经开着的页面。 刚装完一个新扩展、想让它立刻生效时。
extensionSwState(String id) → int 这个扩展的 background service worker 到底起没起。四态分开：
SW_REGISTERED(1) 有 SW 且已注册上 · SW_NOT_REGISTERED(0) 有 SW 但没起来（装是装上了、background 一行没跑）· SW_NONE(2) 清单里本来就没有 SW（内容脚本型扩展，正常）· SW_UNKNOWN(-1) 内核不认识这个 id（没装，或清单在解析那一层就没过）
🔴 0 与 2 必须分开看： 合成一个布尔的话，"内容脚本型扩展"与"SW 起不来"长得一模一样 —— 桌面那次 （FB-P090）正是被这种静默逼着拿三份只差一个字段的清单做对照，查了三轮。
⚠ -1 与 0 也是两回事：-1 说的是 "内核压根没登记这个扩展"，0 说的是"登记了、SW 没起来"。		 装完带 background 的扩展后，想知道它到底跑没跑时。
不改变任何状态，随时可调。

⚠ extensionSwState 是 2026-08-25 新加的（与桌面 C ABI arupa_kernel_extension_sw_state / .NET ArupaBrowser.ExtensionServiceWorkerState 同一套语义）。 旧内核件上没有这个方法 —— 判据用它之前先确认你手上的 AAR 版本。

2.1 Action 面 —— 工具栏那个按钮（2026-08-30 新加，FB-A060）

只有工具栏入口、没有独立主页的 MV3 扩展（截图 / 快速收藏 / 密码填充……）全靠这一组。 在这之前它们装得上、启得动、SW 显示"已注册"，而用户点不动 —— chrome.action.onClicked.addListener 挂得上，但没有任何东西会去触发它。

🔴 为什么点击派发必须内核做，你们模拟不了。 onClicked 的监听器活在扩展的 service worker 里。你们拿不到那个 JS 函数， 也不知道哪个监听器属于哪个权威扩展 id。按插件 id 写死业务逻辑的话，用户"看起来能用" 而插件代码一次都没跑 —— 那不是 MV3 Action 支持，是仿造。
方法做什么什么时候调
listExtensionActions() → JSON 所有该在工具栏画出来的扩展，要画几个入口就是几条：
[{"extensionId":"…","canonicalDirectory":"…","title":"逐风截图", "iconPath":"icon.svg","badgeText":"1","enabled":true,"extensionEnabled":true,"visible":true, "popupPath":null,"sequence":12}]
🆕 +35 起（复核 12）：enabled 是 action 的开关（插件自己 action.enable/disable），extensionEnabled 是你们 setExtensionEnabled 的真值——两格别合并读。 停用的扩展不再出现在本列表（与 Chrome 一致），但 getExtensionAction 单查仍答，带 extensionEnabled:false； 停用/启用那一刻观察者会收到一条快照。停用同时真的停掉它正在跑的 service worker（此前只卸载不停，后台请求会继续涨）。
⚠ popupPath 为 null 表示没有 popup ⇒ 点击应当派发 onClicked。
⚠ MV3 扩展都在里面：上游对 MV3 会给一个默认 Action（清单里没写 action 键也一样），与 Chrome 一致（MV3 扩展在工具栏本来就都有入口， 只是没图标）。别把它读成"清单里写了 action 键的那些"。		 要画工具栏时。

怎么判断你手上这个件有没有它(别看这段话的语气, 去看事实): ① 交付件里的 LATEST.md 那一节有没有提 FB-P123; ② 或者直接试一次 —— 传一个非整数的 tabId, 回 8 就是有, 回 0 就是没有 (没有的时候它会把你给的字符串原样交给扩展, 那正是这条要修的病)。
⚠ 这一段写在这里是为了让你提前按新约定改(改成整数在新旧件上都对); 但**在带 FB-P123 的件到手之前, 码 8 不会出现**。
以下是这条约束的内容: tabId 必须是十进制整数的字符串(如 "42") —— 它会作为整数 tab.id 交到扩展手里(标准 chrome.tabs.Tab.id 就是整数)。不是整数 ⇒ 回 8, 这次派发被拒。
⚠ 内核不发 0/-1 兜底: 那会让扩展去操作别的标签页, 比派发失败坏得多。
⚠ 与 6 分开是刻意的: 6 = "你们没给", 8 = "给了、格式不对"。
⚠ 别用标签页下标当 tabId: 下标会随开关标签页移位, 而 activeTab 的授权 绑在它上面 ⇒ 那是撤销撤错对象, 比撤不掉更坏。用每标签页一个稳定的自增整数。
由来: 此前内核把你们给的字符串原样塞进 tab.id, 扩展拿得到 那个对象, 一转手喂给 tabs.sendMessage / scripting.executeScript 就被参数校验当场拒 —— 实测派进去的真商店包里 36 个中有 10 个死在这一条上。

四条纪律（每条都有它防的那个具体故障）

  1. userGesture 必须 true，缺省按拒处理。 内核不猜手势 —— 由你们如实断言。你们是可信嵌入方：手指点的、还是产品的 AI 点的， 都算你们的手势，那是你们自己的事。插件侧没有任何入口能走到这条路， 所以插件自称有手势是不可能的 ⇒ AI 驱动不需要另一套授权模型。
  2. 🔴 navigationId 每次导航必须换新值。 它就是 activeTab 绑定的 document 维度。不换的话，旧授权会跟着用户 从新闻站走到网银站 —— 那正是 MV3 最小授权模型要防的。
  3. 🔴 撤销是你们的责任，内核不监听你们的标签页生命周期。 它不知道你们什么时候导航、什么时候关标签页。上面那三个 revoke* 漏掉 不会报错，但插件会在它不该有权限的页面上继续有权限。
  4. popupPath 非 null ⇒ 你们去开 popup，内核不派发 onClicked（rc=1）。 MV3 里两者互斥，两样都做的话插件会以为被点了两次，而那种重复在业务侧极难查。
    ⚠ 这一支内核已经授了 activeTab —— popup 里的脚本同样要读当前页。

sequence 怎么用（有一处反直觉）

  • ✅ 同一个 extensionId 的两条快照：号大的是新的 ⇒ 只认号更大的那条。 这样迟到的旧事件就覆盖不了新状态。这是它唯一的用途。
  • ✅ 号全局唯一（一个进程一个计数器，不是每扩展一个）⇒ 不会撞号。
  • ❌ 别拿它跨扩展排先后：注册观察者那一刻的重放推的是各扩展各自的当前号 （历史值），顺序是内部 map 的 id 字典序 ⇒ 在全局看来是乱序的（实测拿到过 5,7,3）。 它们是"现状"不是"刚发生的变化"。按 extensionId 各存各的就无害。

activeTab 与 host_permissions 是两件事，别混

host_permissions（含 <all_urls>）＝清单里声明 → 装的时候用户同意一次 → 常驻；
activeTab ＝一次真实手势 → 只对那个扩展 + 那一个 document 有效 → 导航/关闭/停用即失效。

⇒ activeTab 不是 host_permissions 的严格版，它是替代品。 一个插件想"一直有权限"，标准做法是声明 host_permissions， 不该由 activeTab 去补偿。

还没做的那一半（如实说）

按标签页的 Action 状态没做。MV3 允许 setBadgeText({text, tabId}) 只改一个标签页，而内核现在只有"每扩展一份"。⇒ 带 tabId 的调用内核 如实报错，不静默当成全局设 —— 静默的话插件以为只改了一个标签页，其实改了全部。

划给你们的那几个内核刻意不收：setIcon / badge 颜色 / openPopup / getUserSettings —— 纯渲染或纯 UI 动作， 内核既答不出也不该记。

2.2 接管内核答不出来的 chrome.*（FB-P104）

chrome.tabs / contextMenus / sidePanel / permissions 这几个命名空间的语义内核答不出来（它不知道你们的标签页模型）， 所以内核把调用如实转给你们。你们不接管的话，插件收到的是一句人话 「tabs.query: 宿主未接管这条 API(内核把它转出去了, 但没人接)」—— 那不是崩，插件 catch 得到并能降级，但功能确实没有。

方法做什么什么时候调
setExtensionApiHandler(ExtensionApiHandler h) 注册/撤销接管。传 null = 撤销。回调签名 onCall(int requestId, String extensionId, String name, String argsJson)， name 形如 "tabs.query"，argsJson 是已经过 schema 校验的参数数组 JSON。 内核起来之后注册一次。
respondExtensionApi(int requestId, String resultJson, String error) 答复一次调用。二选一：resultJson 非空 = 成功； error 非空 = 失败（内容会原样出现在插件那边的错误里，请写人话）。 处理完（同步异步都行）必须调一次。

三条纪律（抄的时候别丢）：

  1. 必须答 —— 不答 = 插件那边永远 pending（内核有 10 秒超时兜底会替你回一个错误， 那是兜底不是设计）；
  2. 答成功时 resultJson 是回调参数数组的 JSON —— chrome.tabs.query(cb) 的 cb 收的是一个数组，所以要回 [[{…}]] 而不是 [{…}]。这一层最容易漏；
  3. 答不了就如实回 error，别回一个假的空结果 —— 「调了像是成功了但什么都没发生」比报错难查得多。

可照抄的参考实现（桌面 .NET 版，形状与 Java 一致）： build/roll/mv3-api-probe/host/HostApiState.cs。

它决定扩展的 service worker 与插件自己的页面调 chrome.cookies 时读写哪个分区，也会把 cookies.onChanged 的事件源挂到那个分区。内容脚本（在标签页里）不受影响，仍读自己标签的分区。

四、另外三个坑

🔴 坑 2：扩展 id 不是目录名。 MV3 的 id 有两种来源——manifest 里有 key 时从 key 派生， 否则才从路径派生。本仓实测过 TunnelBear 的 id （omdakjcmkglenbhjadbccaookpfjihpa）就来自 key。

所以：按你自己起的目录名去调 setExtensionEnabled，会静默不生效—— 不报错，用户点了"禁用"而扩展照样在跑。 ⇒ 一律先 listExtensions() 拿权威 id。 （这个方法就是为这件事加的：写启停判据时发现内核根本没把 id 交出来。）
🔴 坑 3：内核不是文件系统监听。 自动下发发生在新 renderer 进程 ready 的那一刻——它扫一次盘，就这一次。

两个直接后果：
  • 同一个页面里刷新不会重扫。刚装完的扩展，用户在当前标签页按刷新——不生效。 要立刻生效就调 rescanExtensions()。
  • 设根晚了不要紧。你在页面已经开着之后才调 setExtensionRoot， 内核会回头补发给那些已经 ready 的进程（日志：扩展根后设 ⇒ 回头补发: N 成功）。 这条 2026-08-25 才真正接上——在那之前"先起页面、后设根"的进程永远拿不到扩展，且零日志。
🔴 坑 4：listExtensions() 回答的是"内核已经认识哪些"，不是"当前根下有哪些"。

两条都别当判据用错：
  • "已登记" ≠ "当前启用" —— 被 setExtensionEnabled(id,false) 禁用的仍在表里。
  • "已登记" ≠ "在当前扩展根下" —— 换了根之后，旧根那些扩展仍在表里。 登记发生在"解析成功并下发过至少一次"那一刻，而这张表只增不减。
🔴 第二条是 2026-08-25 PC 侧实撞的：他们的反测拿"换成空根之后列表应该变空"当判据， 当场红 —— 判据本身错了，不是内核错了。 要判"当前根下有什么"，用 extensionRuntimeSnapshot() 的 items（见 2.3，自 +8）；listExtensions() 只用来拿权威 id。

五、内核提供了什么（以及没提供什么）

内核抽了 chromium 自己的 extensions 层，所以不是我们另写了一套近似实现：

能力由谁执行
内容脚本（matches / run_at / css / all_frames） 上游 ContentScriptsInfo → UserScript → UserScriptSet::UpdateUserScripts ⇒ 官方语义
manifest 解析、权限模型、扩展 id 派生上游 extensions/common
background service worker内核起（chrome-extension:// 资源 loader 已接）
chrome.storage内核 per-plugin 隔离存储（ArupaPluginStorage）
chrome.* bindings / 消息通道内核（renderer 侧 Dispatcher 已装配）
✅ 一句话：标准 MV3 扩展的内容脚本这条路，你不用自己再注入一遍。 如果你的 App 里还留着"页面加载完自己 injectIsolatedJs 注内容脚本"那半（历史侧载路径）， 可以删掉了，让内核官方路径独占——它更完整（带 SW / chrome.* / 消息通道）。
⚠ 但内置插件（不在扩展根之下、内核扫不到的那些）仍走你自己的注入，这个分工是对的。 想让内置插件也享受完整 MV3，把它们也解包进扩展根即可，内核这边不用改。

没提供的 / 要你自己接的：

  • 启停状态不落盘。内核不替你记住用户的选择—— 那是你的插件管理页该持久化的。App 每次起来后按自己的记录重设一遍。
  • 权限判定内核只给结论，不弹 UI。见下节。
  • nomad.* 那组产品扩展指令由交付件里的 plugin-runtime/nomad-plugin-runtime.js 提供（它是唯一一份实现）， 由宿主加载，不是内核 native 面。

六、权限判定（内核给结论，UI 归你）

ArupaMv3Guard.mapPermission(perm) 逐条判清单里的权限：

返回含义你该做什么
0 ALLOW_MAPPED映射到某个受控 cap.*按那个 cap 授权
1 ALLOW_LOW_RISK低风险，直接给放行
2 DENY_PRIVILEGED特权（debugger / nativeMessaging / 阻塞式 webRequest…）拒装或剥权 + 审计
3 DENY_FINGERPRINT_RISK指纹风险（management / cookies / history / <all_urls>）同上。
🔴 management 例外（2026-09-19 起）：不拒，允许启用并弹授权框；用户选完调 ArupaPluginBridge.setExtensionPermissionConsent(id, "management", 同意?)。同意 ⇒ management.getAll 转你们的 ExtensionApiHandler 答真实名单；不同意 ⇒ 内核替代应答 []。授权记录由你们持久化，每次起内核后重新告诉一遍。见 FB-A088。
4 DENY_UNKNOWN内核不认识 ⇒ 保守拒拒
5 VENDOR_NAMESPACEnomad.*：认识，但不该由它答去问对应那套判定（如 checkRoute）

整张表一次拿：ArupaMv3Guard.permissionDescriptions() 返回 JSON，形状是 {version, count, withNote, items:[{name, verdict, verdictName, capability, usable, installable, note}]}，与桌面 arupa_kernel_get_permission_descriptions() 是同一份实现（FB-A080）。version 是内容哈希，缓存后拿它对一下就知道表变没变。这是权限级的清单；方法级的看交付包根目录的 capability-manifest.json。

🔴 5 不是放行。拿到它就当放行，等于凭一个名字前缀发能力。 也别把它当 4（保守拒）处理——桌面 2026-08-19 实跑撞过： 那样做会让加速类插件在装的那一刻就被摘掉权限。 ⚠ 也别自己写前缀判断：边界由内核给，各端各写一份必漂。

checkInjection(...) 判每次注入：

0ALLOW放行
1DENY_NOT_DECLARED清单没声明 —— 不该弹授权，直接拒
2DENY_NOT_GRANTED声明了没授权 —— 这个才该弹授权
3DENY_PROTECTED_SCHEME非 http(s)：内核页 / devtools / file / about
4DENY_PROXIED_HOST被代理接管的域名
5DENY_BROAD_NOT_GRANTED声明含 <all_urls> 但未给全站授权

还有 needsReconsent(old[], new[], granted[])：插件更新后声明范围扩大了要重新征求同意。 防的是一条真实可走的路——装时只声明一个站、用户点了同意，更新后清单悄悄加 <all_urls>。

checkDeclarativeRule(...) —— DNR 规则护栏

你的 declarativeNetRequest 引擎把插件规则接进拦截链之前，逐条经它校验。 它是护栏不是规则引擎本体：它只回答"这条规则准不准装"，不负责执行。

action 入参（安卓这一端 6 种声明式，别只按前 3 种写）：

常量值是什么
ACTION_BLOCK0拦掉
ACTION_REDIRECT1重定向
ACTION_MODIFY_HEADERS2改请求/响应头
ACTION_ALLOW3豁免其它规则的拦截，自身不改请求 2026-08-14 补
ACTION_ALLOW_ALL_REQUESTS4对该框架下的子请求整体豁免 2026-08-14 补
ACTION_UPGRADE_SCHEME5http→https 升级 2026-08-14 补
ACTION_NON_DECLARATIVE99 非声明式（阻塞式 webRequest / per-request JS 回环）—— 永远被拒

⚠ 传一个内核不认识的值，会被当成非声明式处理 ⇒ 拒。所以别自己编 action 码。

返回值：

0RULE_ALLOW这条规则可以装
1RULE_DENY_NON_DECLARATIVE非声明式 action
2RULE_DENY_PROTECTED_SCHEME 模式触及内核 scheme（nomad:// / chrome-extension / chrome: / devtools:）
3RULE_DENY_PROXIED_HOST 模式触及被代理接管的流量，或过宽的 catch-all

七、出问题时看什么

现象先看这条日志多半是
一个扩展都没生效扩展根未设置(没调 …setExtensionRoot)根没设，或设到传输根去了（坑 1）
日志说下发成功，页面里没反应内容脚本待发 … run_at= js= css= 匹配模式=[…]matches 没匹配上当前 URL
装完新扩展刷新没用（没有日志）坑 3 —— 调 rescanExtensions()
点了禁用还在跑扩展已禁用 id=… ⇒ 通知 N 个 renderer 卸载id 传的是目录名（坑 2）
设根晚了没补发扩展根后设 ⇒ 回头补发: N 成功内核版本 < 2026-08-25 那批

八、内核侧验到哪一步（别读成"都验过了"）

桌面侧有一条 runtime 判据（arupa_extdispatch_test）：起真内核 + 真 renderer + 本机 HTTP 页，装一个改 document.title 的探针扩展，从主世界读回 title—— 7 PASS / 0 FAIL，覆盖"内容脚本真跑了 / 后设根补发 / 禁用真失效 / 启用回来"。 两条反测都当场红过（摘掉补发 → 补发那条 FAIL；让禁用不记集合 → 禁用那条 FAIL）。

安卓侧没有等价的 runtime 判据：内核的自检 APK 刻意不起 browser process， 它验的是 Java → JNI → native 这条通路 + MV3 判定 + 插件存储 （交付件字节实跑：MV3 84 PASS / 0 FAIL · 存储 12 PASS / 0 FAIL · 崩溃 0）。 渲染 / 页面里内容脚本真跑没跑，安卓这边结构上验不了——那要真 App。

所以下面这几条只有你们验得了，也正是最该验的：

  1. 一个真实扩展（有 SW、有 chrome.*、有 css）装上去，页面里真的跑起来
  2. 先起页面、后设根 ⇒ 那个已经开着的页面拿到扩展
  3. 装两个扩展只禁一个 ⇒ 被禁的停、另一个照常 （内核测的是单个扩展的开关，"禁 A 不影响 B"没验）
  4. 装完新扩展 → rescanExtensions() → 已开着的页面里生效
